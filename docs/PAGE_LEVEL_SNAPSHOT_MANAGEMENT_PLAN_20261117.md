# 利用 GPU 信号调度快照页工作集：研究 idea 与实施计划

日期：2026-11-17。状态：P1 最小实现完成，等待 kunpeng Full1280 A/C 实验验证；P2/P3 仍为条件阶段。

## 1. 核心 idea 与要回答的问题

**保留现有增量快照和 Linux page cache，通过快照继承关系找出下一次恢复可能需要的页，在 GPU 推理结束前按预算预取。** 优先把有限 DRAM 和 I/O 带宽用于即将恢复的任务及其共享页，而不是仅按快照代际决定整层放在哪里。

研究问题是：在相同 CPU、总 DRAM 和 GPU 配置下，应用掌握的“哪些任务即将恢复、它们共享哪些页”能否比操作系统仅根据历史访问管理缓存，更有效地减少恢复后的阻塞，并提高成功 Tool 吞吐？

第一版使用普通文件 page cache 承载数据，不新增自定义页替换器。只有当实验证明压缩/解压或明确的驻留需求阻碍收益时，才增加小规模解压页缓存。这是可分阶段证伪的研究假设，不预设页级方案一定更快。

例如，两个任务继承同一 Base，都将进入下一轮工具执行，但一个较早、另一个较晚。策略先准备较早任务需要的高优先级页，公共页只发一次读取；较晚任务的私有页留到临近需求时再准备。新增价值来自利用未来需求的在线信号安排内存占用与 I/O，而文件缓存共享本身仍由 Linux 完成。第一版研究页级选择和准备时机，WARM 权威层仍按现有机制保存；它还不是全面替换整代存储的页迁移系统。

## 2. 已有证据与必须澄清的边界

已有三个真实 SQLGlot case、Runtime/Tool 各六代的采样，说明同一地址空间内存在访问异质性。在最终 g6，5/6 个 case/role 组合的某个旧祖先层平均热度高于最新层；因此不能直接把“新”当作“热”。证据见 [页访问实验报告](../.artifacts/snapshot-page-access-20261116/RESULTS.md)。

这些结果尚未证明性能收益，且有以下限制：

- 采样指标是“被访问的窗口数 / 实际驻留的窗口数”。它不能直接反映访问次数、SSD miss 或一次缓存命中的收益。
- g1–g5 只有 1–3 个窗口；g6 有 59–117 个窗口，但它是较长运行阶段的统计，不等于恢复后第一个工具需要的工作集。
- 当前采样器把物理页 PFN 改变也计作访问；迁移、CoW 和共享 PFN 都影响解释。页在运行中写入后可能已经是私有副本，不能把该页后续所有访问都算成旧快照页的缓存收益。
- 图的来源层是恢复时的 lineage 映射；横坐标相同不保证跨代是同一内容版本。未驻留/未观察不应填成“冷”。
- 采样启动开销 p50 1.178 s、p90 5.978 s；不适合给 Full1280 每台 VM 持续启用。既有结果用于提出候选方案，正式性能 run 默认关闭详细页采样。

代码核对得到的实现边界：

| 现有机制 | 对本方案的约束 |
| --- | --- |
| 后代通过硬链接及有效 GPA ranges 引用祖先 | 同一 inode/offset 的 page cache 已由 Linux 共享；不能把已有共享作为新算法收益 |
| WARM 使用 tmpfs，可能保存唯一快照来源 | WARM 权威层不能当成有 SSD 副本的普通缓存随意删除 |
| 当前压缩为独立的 1 MiB Zstd 帧 | 4 KiB 页选择不等于 4 KiB 解压成本；需记录读/解压放大 |
| restore 先展开所需压缩文件组，再建立原生映射 | `WILLNEED` 只能预读文件字节，不能把压缩内容自动变成可供 VM 使用的页 |
| 恢复使用私有映射，碎片过多有 VMA/copy fallback | 第一版不增加逐页 mmap；若以后做 overlay，必须限制映射碎片并报告回退成本 |
| Base 固定 WARM cache 是可选的 host-wide 配置 | 所有对照臂保持相同设置，不能把缓存开关变化混入预取收益 |

当前源码依据：[压缩与展开](../clawbox/cube/snapshot_compression.py)、[生命周期](../clawbox/cube/lifecycle.py)、[GPU 策略](../clawbox/experiments/policy.py)、[配置和跨层机制参考](reference.md)。

## 3. 最小机制

### 3.1 页身份与继承：复用已有权威信息

选择单元是页；执行单元是连续文件范围。

```text
session 的当前 snapshot + role + GPA
                 ↓ 查询有效 lineage range
不可变来源层身份 + 来源文件 offset
                 ↓ 合并相同来源、相邻区间
一个共享预取请求，关联多个等待它的 session
```

缓存去重按不可变来源层与 offset 进行，运行时用实际文件身份校验。不能以 `session_id + GPA` 作为共享键，也不能仅用 inode 号跨删除/重建识别版本。沿用现有 layer/template identity 和引用机制；原生层缺少稳定 ID 时，为其建立实验内注册映射，明确生命周期，不扫描内容做全局去重。

不同版本的同一 GPA 必须分开；一个共享页被某个任务写入后，新的 dirty 页进入该任务的新增量，其他任务仍引用旧版本。版本发布、跨层迁移和引用回收沿用现有顺序，预取请求持有有效引用直到完成/取消。缓存命中与否只改变时间，不改变读出的内容。

### 3.2 先选择简单的候选工作集

第一版用小规模 profiling 产生冻结的 hot-page/range manifest；正式 run 不全量扫描 pagemap/page-idle。

- 模板 Base：仅在模板身份一致时复用 `(template, role, offset)` 的统计。多个真实等待者引用同一个页时，合并读取；不因历史上有很多 rollout 就虚增需求。
- 私有增量：只有当前分支或已验证可迁移的记录才使用页级热度。跨独立运行不照搬私有 GPA 热图；新版本没有观测时标为 unknown，以受限的普通预读处理。
- 使用截至决策时已经产生的历史数据；不能用同一次正式 run 后半段的热图回过头安排前半段预取。已有三个 case 的 manifest 若用于同 case 重跑，标为训练内结果；泛化需要独立 rollout/留出样本。
- 优先关注恢复后首个 Tool 前后的工作集。现有累计热图缺少逐页时间顺序，不能从中恢复首次访问时间；如该信息影响决策，再增加少量定向采样，不先扩展 Full1280 日志。

第一版每次只从即将恢复的会话中选有限范围。可用一个无需训练的候选分数：

```text
priority(range) = sum(等待者对该 range 的有效访问概率) / 预计新增读取字节
```

它只用于同一临近恢复队列内排序，并非精确的延迟收益模型。已驻留范围不计入新增预取；估算驻留状态使用有上限的查询，失效时正常按需读取。每个会话设独立上限，避免热门 Base 抢完配额；实际 Tool-ready 请求的必要 I/O 优先于推测预取。

后续若静态选择确有收益，可加 2-bit 热度：有有效观测且访问则加一，观察到未访问则减一，缺测则保持；达到高阈值才优先保留，降到低阈值再降权。仅对有界候选集合更新，不能把“改到 checkpoint 时全量扫描”当成低开销。此扩展不作为第一组结果的前提。

### 3.3 根据 GPU 事件决定何时预取

调度同时考虑“需求有多近”与“当前是否有闲余 I/O/内存预算”。最初只改变页准备时机，保持原有 VM 回收和恢复策略，以便分辨收益来源。

| 可用信息 | 动作及边界 |
| --- | --- |
| model wait / `queued` | 登记下一次需求、构造候选；`est_wait_s` 目前主要描述 prefill 排队，不能当完整响应剩余时间 |
| `first_token` | 可作阶段事件策略的一种触发；不能宣称请求即将结束，记录因此提前占用的内存时间 |
| 有可信来源的 `think_end` | 可触发受限预取；没有这个事件的请求不能伪造边界 |
| 公共接口提供有效的完整响应完成时间预测时 | 才启用 deadline 模式，并记录预测来源、年龄和时钟换算 |
| 最终响应 ready | 立即走正常 demand restore；不为等待推测预取而延迟执行，复用已完成的准备工作 |
| 取消、过期、请求切换 | 停止未发出的预取，释放预留；已经发出的 I/O 计入成本，不能假定取消能撤回它 |

deadline 模式使用：

```text
开始准备时间 = 预计完整响应时间 - 实测准备服务时间 - 安全余量
```

准备服务时间来自本机近期已完成的读盘/解压阶段，并含必要排队余量；GPU 剩余时间只能来自模拟器公开接口。接口不足时采用明确标记的事件模式，报告覆盖率，不读取 trace 的未来时长或模拟器内部未来队列。

已有整 VM prewarm 与页预取共用请求身份和生命周期锁。相同页/压缩组最多一个准备任务；不得出现预取和常规 restore 各解压一次、重复启动 VM 或提前释放未完成的响应。

### 3.4 复用 page cache 的执行路径

对于已有可映射原始文件：按 4 KiB 选择页，将同文件、连续 offset 合并为有界 range，使用 `readahead`/`posix_fadvise(WILLNEED)` 或有界后台读取。第一版不改变 VM 的 lineage 映射，因此不会因每页 WARM/COLD 切换新增海量 VMA。

对于仍为压缩容器的组：先区别“读取压缩字节”与“产生可用的原始页”。第一版沿用现有完整文件组展开，复用已展开结果；若将该阶段提前，必须纳入原有容量 reservation、锁和发布屏障，并单独报告它的整组成本。仅靠选择热页不能宣称减少了解压量。

预取完成/系统调用返回不等于页一定仍驻留，更不等于 VM ready。用必要阶段时间和采样式驻留检查判断效果；不在控制回调内等待全量检查。

第一版让内核自行回收，不主动对运行中 guest 内存执行 `MADV_DONTNEED`：私有 dirty 页可能因此丢失。`FADV_DONTNEED` 也只是建议，不能当作精确释放或容量保证。后续若增加定向回收，仅作用于已确认可重新构造、无活跃使用的干净文件缓存。

## 4. 容量、公平性与低开销要求

采用两级约束：

1. 保持相同的实验总 DRAM 上限及 NUMA 布局，用主机/父 cgroup 的实际占用检查是否超预算；共享文件页通常不会按每个消费者重复计费，必须确认实际 charge 所属。
2. 在该上限内，限制“本策略申请/在途的预取字节、解压扩展空间和并发 I/O”。这是预取工作额度，不是声称能精确限制 Linux 全部 page cache 的驻留量。

总 DRAM 口径包含 live VM 私有页、WARM tmpfs、COLD 文件 page cache、压缩文件缓存、解压产物缓存、控制面与采样元数据。tmpfs 的 shmem 可能已包含在 cgroup `file` 内，不能再直接相加。跨进程 RSS 也不能求和代替共享页去重。既有外部占用应固定或单独列出。

预取线程和解压进程须进入既定资源记账范围；不能让 helper 在限额外把 page cache 预热后再比较。GPU 模拟器 CPU 与 ClawBox/VM 的隔离和配额在各臂一致。

每轮候选数量、range 数、在途字节和带宽都有上限；合并重复信号。压缩帧和已存在映射粒度不改成“一页一个文件”。在内存或 I/O 压力下首先撤销推测性工作，必要 demand restore 优先。

## 5. 实施顺序与交付

| 阶段 | 工作 | 完成条件 |
| --- | --- | --- |
| P0：确认机会 | 用已有 Full1280 日志拆分恢复队列、读盘、解压、映射、sidecar/首 Tool；核对实际页缓存、压缩复用和已有整 VM prewarm 覆盖 | 确认可被页准备改善的等待或额外驻留成本；若现有 prewarm 已充分覆盖，或主要是无关 CPU 控制开销，先记录负结果，不大改存储 |
| P1：最小原型 | 实现 lineage range resolver、冻结 manifest、共享去重、有界预取队列和事件触发；只接现有 workflow | 小规模真实 VM 正确性通过；新增开销有界；预读与展开分别计时 |
| P2：Full1280 对照 | 固定 workload/预算/版本，完成 A/B/C 中必要对照并保留日志 | 能解释收益来自选页、时机还是全组提前展开，并给出同预算结果 |
| P3：条件扩展 | 仅在 P2 证明残余瓶颈来自解压/驻留时，研究小型解压缓存或 2-bit 更新 | 若条件不成立，P2 就是交付终点；无需把所有备选功能实现完 |

实现入口应集中在现有 `experiments/spec.py`、`policy.py`、`worker.py` 与 `cube/lifecycle.py`；候选解析和预取器放入独立的活动模块。复用 `snapshot_compression.py` 的原子发布/复用机制。只有在确需扩展原生 restore/解压时才改 ClawBox 维护的 CubeSandbox patch/helper。

当前未提交的页采样改动及用户工作保留。执行时核对最新 ClawBox、sim-release 与本地修复，冻结到独立实验版本，运行过程中不换代码。sim-release 上游不修改。

新增功能必须在现有 experiment schema 内有公开配置，更新 [操作指南](guide.md) 与 [选项参考](reference.md)，提供可按顺序执行的命令。首次交付默认关闭，不把研究功能自动开启到普通实验。

### 拟新增配置

建议归入 `execution.snapshot_page_management`，以下名称和默认值是设计起点，尚未被当前代码支持：

| 字段 | 初始默认/要求 | 单位与用途 |
| --- | --- | --- |
| `mode` | `off` | `off / immediate / gpu_event / gpu_deadline`；缺少完整响应预测不能启用 deadline |
| `hotset_manifest` | `null` | 文件路径和摘要；指定模板/role/观测来源，未知页保持 unknown |
| `prefetch_budget_mib` | 启用时显式填写 | 全局推测性准备额度，来自已有 DRAM 余量，不能从机器总容量猜测 |
| `per_vm_prefetch_mib` | 32 | 每 VM 候选页字节上限，单次小验证后冻结 |
| `max_inflight_mib` | 128 | 全局在途 I/O 上限，实际值不超过剩余预算 |
| `io_workers` | 2 | 后台 I/O 并发数，不占满 demand 通道 |
| `prefetch_bandwidth_mib_s` | 64 | 全局限速初值，需记录实际带宽和平台影响 |
| `max_ranges_per_vm` | 256 | 限制碎片和系统调用数量；范围截断单独计数 |
| `deadline_margin_seconds` | 0.2 | 仅 deadline 模式使用的初始余量，不能拿它代替准备服务时间 |
| `signal_max_age_seconds` | 沿用现有有效期配置 | 事件过期后失效推测性计划，避免重复定义不同的有效期 |

以上数字是保守的原型上限，不是已验证最优参数。第一组对照前冻结一次，避免每次小调参都重跑 Full1280。Python 策略变化通常不需 guest 镜像重建；原生 helper/patch 改动需对应 host 组件构建安装和能力验证；所有性能对照均使用新 run ID。

## 6. Full1280 实验设计

### 对照组与运行数量

| 组 | 机制 | 要回答的问题 |
| --- | --- | --- |
| A | 当前已支持的整代 WARM/COLD + Linux page cache + 原有 GPU prewarm | 基线；不关闭原有功能人为制造收益 |
| B | A + 同一候选页选择，在 model wait 后尽早启动受限准备 | 知道读哪些页是否有帮助，提前驻留成本是多少 |
| C | B 的同一候选集合/上限，按 GPU 事件或有效 deadline 安排准备 | 时机是否减少等待或内存占用，是否降低无效预取 |

所有组保持相同的 checkpoint/compression/VM prewarm 语义；整组提前展开若作为新增能力，应在 B/C 一致开放并单独计量。静态 Base cache 开关和容量也完全相同。

先一轮 A、一轮 C 看端到端信号；只有 C 有收益或需要定位负结果时再运行 B。没有可比的同版本基线时不以旧历史 run 代替 A。首轮原则上不超过三轮正式 Full1280；若出现值得验证的效果，再对关键 A/C 配对做一次独立重复，报告波动，不将单次差异当作统计显著性。

仅做 CPU 生命周期定位时可不用 GPU 模拟器，复用已冻结、来源明确的模拟器时序；涉及上述协同收益的 A/B/C 必须使用实时 sim-release。LLM 耗时由模拟器产生，推理预测来自公开模拟器信号；保持 `k=1` 和实际 prompt，不使用原 trace 的 LLM 时长加速测试。

### 工作负载与环境冻结

- 使用常用 Full1280，通过 `clawbox experiment` 启动，每轮新 ID。冻结 case/rollout 映射、工具输入、到达时序、随机种子、模板、CPU/DRAM 预算及 GPU topology/engine 数。实际 dispatch 映射必须核对，不能看到 1280 就写成 80×16。
- 主对照使用最近正式 Full1280 的实际 workload；如果它不是 80 case×16 rollout，明确写出实际构成。80×16 的共享强度实验另设显式 workload；同 case 多 rollout 不自动等于从同一个运行中快照分叉。
- 复用 [kunpeng creation baseline](../.artifacts/experiment-standards/kunpeng-creation-20261108/manifest.json)：官方 kernel `6.6.0-145.1.28.165.oe2403sp1.aarch64`、IRQ batching/legacy IRQFD、display-off、兼容模板、至少 2560 实际 Ready/unowned TAP、CubeAPI NOFILE ≥65536。后续 native 变化另记摘要。
- GPU 使用最近经验证的大容量配置并在各组固定；记录实际请求队列和利用率，不能只凭 engine 数说资源无限。网络访问与 dependency-install gate 保持此前完全放开的配置。
- 不人为强制本次 profiling 的六代交替序列。使用常规压力触发的 snapshot；比较真实 checkpoint/restore 数及并发覆盖。若缺少快照操作，报告条件未覆盖；需要改变压力时，对所有组同样改变并单列实验。
- 默认取到达阶段后的共同 40 分钟窗口；保存完整轨迹，并按共同 session/call 阶段补充比较。配置 1280 不等于始终有 1280 同时执行，报告实际 active/tool-running/parked 数。

page cache 初始状态和 NUMA 分布必须可比。第一组使用一致的预热/启动顺序并记录初始占用；共享 inode 可能让前一轮为后一轮预热，因此解释顺序效应，关键重复交换 A/C 顺序。不能全机 `drop_caches` 干扰其他项目。若需冷启动对照，仅在闲置、明确归属的文件范围清理干净缓存，且验证实际驻留变化。

### 指标与判定

主要指标是最终响应已可交付之后，因恢复/页准备而新增的等待，以及成功 Tools/s、完成 session 数。真实 Tool 计算或正常 CPU admission 等待要分开；没有 Tool 的响应不虚构首 Tool 时间。

每组至少报告：

- checkpoint、restore 各阶段及 exposed resume wait 的 p50/p90/p99、样本数、超过 1 s 比例；后台准备的服务时间另列，不能仅把工作移到后台就声称成本消失。
- 成功 Tool 吞吐、LLM 完成 QPS、失败/取消、VM 状态曲线，统一时间窗口。
- SSD 实际 read/write bytes/IOPS、解压 CPU/字节、major faults、预取字节、取消后浪费、page cache 命中/驻留的可观测部分。普通预读返回值不是命中证据；观察不到真实使用时标为 unknown。
- 总 DRAM 峰值、时间积分、额外文件缓存、NUMA 分布；cache residency 不能用 live RSS 简单替代，采样式唯一 inode/offset 核对与父级总量交叉验证。
- 页准备决策 CPU、队列长度、回调时间、预测覆盖率、实际 ready 相对预测的误差及提前准备时间。
- 可比会话的写入/覆盖/继承、layer 数、共享范围和 GC；证明性能变化未依赖丢页、跳过压缩或改变工作负载。

预先采用以下研究判据：新增策略回调 p50 <10 ms、p99 <100 ms 为目标；新增控制 CPU 不超过给 ClawBox/VM 分配的 CPU 预算的 1%。p50 <1 s 仍是主要生命周期 overhead 的目标，达不到时明确瓶颈。100 ms 的单次波动不触发早停。

方案值得继续的初步信号为：同预算下 exposed resume wait p50 降低至少 20%，或成功 Tools/s 提高至少 10%，或相同吞吐下实际 DRAM 时间积分降低至少 10%；同时失败率与 p90 不发生实质回退。阈值是事先确定的研究门槛，最终判断结合重复波动；不能把不同预算结果混为同预算增益。

若 SSD misses 很低、压缩展开占主导、GPU 等待没有足够提前量，或 C 无收益，则给出对应负结果及成本拆分。仅提高缓存命中而没有等待/吞吐/占用改善，不足以证明系统收益。

## 7. 条件二期：解压后的页缓存

只有 P2 数据显示以下需求时进入：可用热页无法通过普通 page cache 准备，或者整组解压的 CPU/写入放大成为主要阻塞。

设计为保留 COLD 压缩来源、增加有界 WARM 解压块缓存，版本身份和引用关系仍复用现有 lineage。首先保持 1 MiB 帧为解压单元，按热点选择块并测量放大；只有浪费明显才研究更小帧/页 overlay。解压缓存优先验证，暂不同时改帧大小、替换策略和 GPU 调度。

必须先实现“未准备页的正确读取路径”。当前普通 mmap 一个尚未填充的稀疏文件会读到零，**不能用文件空洞冒充未来可按需解压的页**。需要明确的缺页填充机制，或在发布给 VM 前完整准备它可能映射的内容。前者涉及 native restore/pager 与并发正确性，是独立工作量，不能包装成简单的 fadvise 改动。

只有 COLD 副本已发布且完整时，WARM 副本才可丢弃。不得删除活跃 VM 仍可能访问的 backing，或在 MAP_PRIVATE 脏页上做破坏性回收。父快照清理不得影响存活子代；引用/映射结束前保留来源，按现有层级 GC 回收，暂不实现文件内逐页打洞 GC。

此阶段与 A/C 比较时，把新增 SSD 写入、保留压缩副本、解压缓存、原始文件 page cache 的全部成本计入；复制到 tmpfs 可能形成双份 DRAM，不能仅比较 WARM 目录大小。

## 8. 验证、轻量证据与停止条件

先完成一个有限的真实 VM 往返验证：共享 Base、两个独立后代、冷热混合、普通写和写零覆盖、父快照删除后子代恢复、预取取消/过期、缓存缺失、压缩组去重展开。检查返回内容和成功工具结果。相关单元测试覆盖范围解析和版本隔离；没有涉及原生组件时不重建镜像或重复完整 host apply。

正式日志保持每个状态变化一条：`session/request/role/snapshot/source_layer`、信号类型/来源/年龄、候选/选中/在途字节、共享等待者数、排队/开始/完成时间、准备阶段和退出原因。Unix 时间用于跨进程对齐，monotonic 时间用于本机时长；lineage 每次发布保存压缩 range manifest，热点 bitmap 只在版本变化时保存。

每 5 秒聚合吞吐、VM 数、CPU、内存及 I/O；不逐页打印 JSON，不记录每条重复 queued 信号。详细首触/访问验证仅在少数独立 profiling session 中开启；不能将其结果当正式 Full1280 的无仪器开销指标。

遇到错误页版本、引用提前回收、无效范围当零、重复恢复、数据损坏、预算失控或 host 故障应提前停止，保留失败证据并修复。普通延迟波动继续测量；观测窗口已足以证明无收益且原因明确时结束该 arm，使用共同窗口解释，不反复重跑同一条件。

最终交付：可关闭的最小实现及配置说明、同预算 A/C（必要时 B）数据、开销与吞吐曲线、页候选及继承证据、预测覆盖和误差统计，以及明确的“继续二期 / 到此为止”判断。若假设不成立，负结果和清楚的原因同样是有效交付。
