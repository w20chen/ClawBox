# Full1280 开销、吞吐与页级继承观测计划

日期：2026-11-16。状态：待用户发出执行指令；本文件不启动实验。

执行窗口从后续开始执行的时刻 T0 算起，最多 6 小时，包含准备、构建、
实验、分析、清理和交付。达到目标即可提前结束，不为用满时间重复实验。

## 1. 目标与执行授权

在常用 Full1280 工作负载和实际资源约束下，优先消除限制吞吐的开销：

1. 各主要 CPU 生命周期、控制面和 CPU–GPU 协同开销分别达到 **p50 < 1 s**，
   并尽可能继续降低；同时报告 p90/p99、样本数和超过 1 s 的比例。
2. 解释并改善“1280 个并发任务，实际执行工具约 100 个，约 40 tools/s、
   LLM 低于 10 calls/s”的现象。这些数字是待复核的用户观察，不预设根因，
   也不把增加驻留 VM 数本身视为吞吐改善。
3. 保持压缩、增量快照、COLD SSD/WARM tmpfs 的按页共享和回收正确性。
4. 用轻量事件和 timestamp 重建同一 RL 场景的快照继承及层驻留变化，
   覆盖例如 80 个 base 场景、每个 16 个独立 rollout 的 1280 会话。

**执行期间发现问题，应自主定位、修复并验证。** 授权范围包括 ClawBox
实现、ClawBox 维护的 CubeSandbox 补丁、实验配置，以及 GPU 信号驱动的
沙箱调度机制；不因常规修复、构建、配置调整或必要验证反复等待用户确认。
修复应以证据为依据，优先处理影响正确性、实验推进和吞吐的最大问题，
不扩展为无关的生产化改造。

保持 sim-release 上游源码不变；适配放在 ClawBox 一侧。遇到只能通过修改
上游或改变任务要求才能绕过的问题，保留明确证据和限制，不假报已解决。

## 2. LLM 时间与预测的最终约定

此处采用用户最后的纠正，取代“LLM 耗时与原始 trace 一致”的早先要求：

- **LLM 实际耗时直接由实时 GPU 模拟器产生。** 原始 trace 用于工作负载、
  响应和 token 等回放输入，不用于在 ClawBox 中强制推理耗时。
- 保持模拟器虚拟时钟 `k=1`；`time_scale` 缺省或为 1。ClawBox 不补加 trace
  sleep、不加速 LLM、不根据事后完成时间提前触发调度。
- 推理及排队预测来自模拟器接口。CPU 工具自身的预测继续使用现有
  ClawTune/ToolKB 路径，不能把两类预测混为一谈。
- 模拟器没有提供的预测明确标为未知，不能填零或冒充精确剩余时间。
  允许使用模拟器已提供的在线事件、估计、实际完成反馈和本机实测切换成本
  调整决策，但不读取未来 trace 或模拟器内部未来事件队列。
- 端到端保留 `prompt_source=actual`、请求/会话/trace/call 绑定和实际工具执行。
  区分模拟器排队、模拟推理、模拟器宿主 CPU 延迟、通信及 ClawBox 控制开销。

## 3. 实验约束与比较方式

### 固定条件

- 统一使用已有 `clawbox experiment` 工作流、Full 策略和并发 1280，
  每轮使用新 run ID，保留冻结配置、版本、输入摘要、qualification、事件和 ledger。
  小规模测试仅用于修改后的必要正确性检查，不能代替高并发性能结论。
- 复用 `.artifacts/experiment-standards/kunpeng-creation-20261108/manifest.json`
  对应的 host plan、profile、兼容模板及正式参考 spec。固定官方 kernel
  `6.6.0-145.1.28.165.oe2403sp1.aarch64`、IRQ route batching、按需 legacy IRQFD、
  display-off 启动设置；Full1280 前验证至少 2560 个实际 Ready/无主 TAP，
  CubeAPI NOFILE 至少 65536。
- 保留已有 checkpoint/restore 修复、压缩和模板。不通过跳过持久化、引用校验、
  同步完成屏障或资源约束压低测量值，不重新引入压缩侧全零页扫描。
- 成对比较固定 workload、base/rollout 映射、到达时刻、随机种子、CPU/内存预算、
  模板与 GPU 拓扑。修改其中一项必须记录为实验变量，不能与代码优化混报收益。
- T0 核对远端最新 ClawBox、sim-release 及当前未提交修复，保留工作树后同步到
  独立实验版本并冻结 commit/补丁/二进制摘要；一轮运行期间不更换代码。

### 两种 Full1280 模式

| 模式 | GPU 模拟器 | LLM 时间来源 | 可以证明什么 |
|---|---|---|---|
| CPU 专项 | 不启动 GPU 服务 | 复用同工作负载、已冻结的模拟器原生耗时序列 | 生命周期、控制面、资源准入和存储开销 |
| CPU–GPU 协同 | 实时运行原生模拟器 | 模拟器当前负载下实际产生的时间与在线信号 | 完整吞吐、信号利用、切换策略及反馈循环 |

CPU 专项不得退回原始 trace 的 LLM 时长，也不得零延迟跳过 LLM。优先复用
已有可信的模拟器记录；没有匹配记录时，先做实时 GPU Full1280 建立基准，
再导出只供回放端使用的耗时序列。序列不暴露给 CPU 调度器作未来信息，
也不把通信/ClawBox 开销重复算进 LLM 时间。若现有回放端不支持，做最小的
公开配置适配并记录来源。冻结时序会切断 GPU 反馈，不能据此宣称整体吞吐改善。

默认预算为至多两轮 CPU 专项和两轮实时协同 Full1280，不机械执行四轮；
基准可复用则减少轮次。修改先合并，再做对应验证，禁止逐个微调后反复重跑。
每次新运行都必须回答明确的问题。

高并发比较需覆盖计划到达阶段之后、实际活跃会话仍足够多的共同时间窗口，
报告 offered/admitted/live/tool-running 数量，不能只因配置写了 1280 就称高并发。
优先让实验正常推进。受 6 小时上限限制的截断结果标为未完成；使用匹配窗口、
共同调用/工作量对照，披露未完成与失败，不能把快完成的子集当全体结果。

## 4. 已知起点与待验证假设

已有 16 对 VM 定向结果中，Runtime/Tool checkpoint 最大 0.653/0.753 s，
restore 最大 0.270/0.356 s；Tool destroy p50 0.969 s、最大 1.303 s。
跨 COLD/WARM 的五代继承、写零覆盖和共享层引用测试已通过。
**这些不是当前 Full1280 已达标的证据。** 详细证据保留在
`.artifacts/lifecycle-subsecond-20261116/RESULTS.md`。

当前代码可见的重点检查项：

- GPU 回收候选主要依赖 `queued.est_wait_s` 的有效 prefill 估计；缺失或过期
  估计会使候选不足，可能造成有等待任务却无法释放内存。
- 预恢复主要由可信 `think_end` 驱动。缺少 reasoning 边界的 trace 可能没有
  该事件；不能假定所有请求均能提前恢复，也不能把 `first_token` 当成即将结束。
- Runtime 与 Tool 预恢复目前有串行关系；检查哪些依赖确实必须串行，
  哪些可以在同一合法预算内重叠，不能简单同时放行导致内存超额。
- 既有 Full1280 配置曾使用 `8A` 拓扑、4 个真实模拟器 CPU、GPU 回收阈值 1 s、
  信号有效期 5 s，以及 checkpoint 并发 24。执行前核对实际生效配置，
  区分 GPU card/engine/instance/副本数、真实 CPU 核数、运行中请求数和队列长度。
  配置数字不是已利用能力。
- Full1280 的多线程控制、全局锁、生命周期并发门、API/sidecar、GC、页映射和
  磁盘带宽在负载下可能放大延迟；32 VM 结果不能排除这些问题。

## 5. 开销与吞吐的测量口径

### 每处 overhead

按 Runtime/Tool、COLD/WARM、创建/恢复路径和阶段分别统计，不用混合中位数
掩盖慢路径。保留请求入队、开始执行、服务完成及可继续运行的时间。

| 链路 | 必须拆分的部分 |
|---|---|
| 创建与 ready | 创建排队、API/native create、放置/cgroup、Agent/sidecar ready |
| checkpoint | 策略队列、锁/transfer slot、pause RPC、脏页与层发布、压缩/fsync、旧层清理 |
| restore | 准入/解压空间等待、解压、映射/native restore、放置、sidecar 重连、首次 Tool 可执行 |
| 回收与迁移 | WARM spill、共享内存借还、NUMA 迁移、GC、task 删除、cgroup 清理 |
| 工具调度 | 请求已具备输入到执行开始；预测 RPC、CPU/内存准入、dispatch、结果回送 |
| CPU–GPU | 请求提交、事件产生/发送/接收、callback、策略排队、决策、生命周期动作、回复交付 |

同时报告服务时间、等待时间和用户可见的连续阻塞时间；不能通过只测 RPC、
把等待挪到后台或遗漏 sidecar readiness 来达标。并行/嵌套阶段不重复求和。
真实工具执行及原生模拟推理不计为控制 overhead；资源容量导致的排队独立呈现，
并继续判断该容量是否被过度保留、失效记账或不当策略人为压低。

### 为什么只执行约 100 个工具

建立每个会话的主要阻塞原因时间线：未到达、等待准入、LLM 排队/执行、
等待 CPU/内存、checkpoint/restore、控制面等待、Tool 执行、完成/失败。
重叠工作另行关联；无法归因的时间显示 unknown，不能自动归入 LLM。

在同一个窗口统计：

- 成功完成 tools/s、LLM 完成 calls/s，同时给出提交率、重试、失败、取消和 token/s。
  模型调用、对话轮次、一次响应内的多个 Tool 调用分别计数。
- 时间平均的 Tool-running、ready-but-waiting、LLM in-flight 数量及各状态 session-seconds。
- CPU 实际使用核数、runqueue、cgroup throttle、NUMA/内存压力、SSD 带宽/IOPS，
  模拟器真实 CPU/loop lag，以及模拟 GPU 各 engine 利用和排队。
- 切换次数/Tool、checkpoint 后很快恢复次数、预恢复命中率、提前驻留时间、
  LLM 已结束但 Tool 仍未 ready 的暴露等待、每次回收实际释放的物理内存。

用均值和状态积分检查 `平均执行中工具数 ≈ tools/s × 平均工具执行时间`，
结合每个 LLM 调用对应的工具数量解释吞吐关系；不要拿 p50 代入这一关系。
从实际 ready backlog 判断供给不足还是处理能力不足，再区分 GPU 服务容量、
GPU 宿主模拟速度、CPU 调度、内存策略和控制面问题。不预先承诺任意倍数提升。

## 6. GPU 信号调度机制允许调整

**自主调整 ClawBox 如何利用模拟器预测和事件是本任务的明确范围。**
先检查最新接口实际提供的字段与语义，再优先利用下列信息；对新增接口采用
同样的来源、有效期和请求绑定校验。

| 信息 | 可用于的决策 | 必须保留的边界 |
|---|---|---|
| `queued`、rank、layer、`est_wait_s` 及估计依据 | 选择等待较长且有回收收益的候选 | 当前估计主要描述 prefill 工作，不等于完整模型剩余时间；KV/Decode 等待可能未知 |
| `prefill_start`、`first_token` | 更新阶段、失效旧排队估计、调整回收优先级 | 不假定 decode 很短，不把首 token 当最终回复 |
| `think_start`、`think_end` | 有可靠边界时安排提前恢复 | 检查来源与覆盖率；不存在的事件不能伪造 |
| `finish`、最终响应 | 停止回收、推进恢复和工具调度 | P-leg finish 不是完整请求结束；最终响应保持正确性兜底 |
| 公开的中断/重算/迁移及 engine 状态（若提供） | 失效过期判断、更新预期和资源分配 | 仅使用接口真实暴露的信息，不能读取内部未来状态 |

重点尝试方向按测量结果选择，不一次同时改变所有因素：

1. **减少没有收益的切换。** 根据真实内存压力、预计空闲窗口和近期实测
   checkpoint/restore 成本决定是否回收；短等待优先驻留，长等待且有实际
   待准入任务时更积极释放。增加必要的滞回或最小驻留窗口，避免反复换入换出。
2. **减少恢复过晚。** 根据模拟器可用的剩余时间估计/阶段边界，为恢复成本
   留出时间；按预算预恢复，优先即将产生工作或已具备工具输入的会话。
3. **处理信号缺失。** 测量无估计/无 think_end 的比例和受阻会话。
   可以采用基于当前 GPU 事件、已等待时间和真实压力的事件策略；明确它是
   不依赖精确剩余时长的调度规则，不伪称模拟器给出了缺失预测。
4. **降低调度动作自身成本。** 回调只更新必要状态并投递动作；合并同一请求
   的过期排队更新，保留关键阶段和最终事件；避免全会话扫描、锁内 IO 和重复 RPC。
   不让后台排队隐藏在“callback 很快”的指标后面。
5. **判断 engine 配置是否是容量瓶颈。** 先在固定拓扑下排除宿主 CPU/控制面
   问题；只有数据支持时才做公开配置可表达的拓扑或并行度对照。
   GPU 扩容带来的吞吐变化单独报告，不归功于 ClawBox 优化。

信号过期、重复、乱序、请求更替及终止后的事件不得重复触发生命周期操作。
保持 host 持有模型流，VM checkpoint 不能取消正在进行的 GPU 请求。
新阈值或策略必须有公开配置、单位、默认值、来源及触发原因，不能藏在脚本中。

## 7. 页级继承的轻量日志

### 工作负载与身份

先固定 80 个有效 base 场景和每个 16 个 rollout，使用现有 `grouped` assignment
与 `rollouts_per_case: 16`，冻结实际 case、模板和到达映射。若常用 Full1280
原先采用另一映射，新分组作为新的共同 workload，所有比较臂使用同一映射。
不能把新分组结果直接与旧 round_robin 数字当作成对比较。

`base_case_id` 表示 RL 场景，`base_snapshot_id` 表示实际共享内存基底，二者
不能混同；每个 rollout 的 Runtime/Tool 可变状态独立。按已有实际继承关系
记录，不为了画树而新造共享 checkpoint 或改变工作负载语义。

### 记录与重建

逻辑快照继承通常形成树/森林；多个快照共享物理层时，实际关系是有向无环图。
日志同时支持两者，不把多处共享关系展开成假的独占副本。

| 事件 | 最小必要信息 |
|---|---|
| run/base 注册 | run/attempt、host、workload 摘要、case/rollout、Runtime/Tool、实际根快照与模板身份 |
| `snapshot_published` | snapshot ID、父 snapshot ID、generation、角色、目标 tier、关联操作 ID、full-base 标志与原因、新脏字节/搬运字节 |
| 层创建/引用变化 | 稳定 layer ID、真实 backing 身份、继承/新增/覆盖区间的紧凑表示、逻辑/分配/压缩字节、层所在文件系统与 tier |
| 层迁移/复制 | 原/新 layer ID、from/to tier、保留共享还是新拷贝、复制字节、开始/完成与状态 |
| restore、引用释放、GC | 被恢复快照、增加/解除的引用、实际回收层 ID、原因和完成状态 |

所有事件包含 Unix timestamp、进程内 monotonic timestamp、进程实例与递增序号。
跨进程按操作/快照/层 ID 关联，不能直接相减不同主机的 monotonic 时钟。
沿用现有时钟偏差/不确定度记录区分 GPU 事件发生、发送和 CPU 接收。

一个快照在 WARM，不代表所有继承层在 WARM：必须记录**每层**的实际位置。
硬链接别名和压缩表示更换保留可追踪身份；WARM→COLD 拷贝生成新物理层，
记录其来源。inode 只作身份佐证，避免删除后 inode 复用造成串联错误。

只在已有状态提交/生命周期边界记录，不扫描 RAM、不逐页打印、不在每次
采样中重复整个继承图。从现有 lineage 元数据获取区间，新增/变化区间紧凑
存储，引用不变部分；确保父元数据被清理后仍可重建，不只记录将被删除的路径。
零值脏页的覆盖关系照常保留，不能按内容把它从继承关系中漏掉。

默认紧凑 JSONL 加可复用的区间 sidecar，后台批量写、定期 flush、退出收尾，
不做逐事件 fsync。所有拓扑变化完整记录，资源统计默认每 5 s；计数和摘要
可在更低成本下聚合。显式记录日志丢失/队列溢出，不能默默得到“完整树”。
测量日志 CPU、写入字节和排队耗时，目标为不使 tools/s 或关键阶段 p50 恶化
超过约 1%；短噪声窗口不作达标证明。若成本偏高，先压缩重复元数据和批处理，
不删掉重建所需的继承边。

交付离线重建脚本和一个真实 base 的树/DAG示例，支持按时刻查看各层 COLD/WARM
驻留、共享关系、独占/共享物理字节及回收；不读取内存内容。

## 8. 最多 6 小时的执行顺序

阶段顺序可因证据调整；若 CPU 专项缺少模拟器时序，先执行实时 GPU 基准。
构建和分析尽量利用实验运行期间完成，部署只在相应实验结束并清理后进行。

| 相对时间 | 工作 | 产出/转入下一阶段的条件 |
|---|---|---|
| 0:00–0:25 | 核对最新版本、当前修复、主机及 workload；复用既有数据；补齐必要低成本计时与继承日志 | 冻结比较条件、主要假设和运行清单 |
| 0:25–1:35 | Full1280 基准，在线分析等待与利用率；准备已定位的大开销修复 | 以累计阻塞时间和吞吐影响排序的问题列表 |
| 1:35–3:00 | 合并 CPU/存储/控制面修复，必要正确性测试，一轮 Full1280 验证 | 高并发各路径分位数、CPU 开销和正确性结果 |
| 3:00–4:15 | 实时 CPU–GPU Full1280，核对预测/事件覆盖、队列与实际执行数量 | 完整状态时间分解及主要吞吐瓶颈 |

## 9. 验收与交付

- 在真实高并发窗口，列出所有已发生的主要开销路径的 p50/p90/p99、样本数、
  等待与服务时间。目标逐项 p50 < 1 s；无样本的路径写“未验证”，
  未达标路径附根因与阻塞贡献，不用总体平均掩盖。

  不能仅以“设计如此”结束调查。

  回收正确；并发故障的定向测试与正式 workload 校验分别报告。
